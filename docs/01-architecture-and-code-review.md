### 0.2 架构上的评价

做得对的：

- 三个新模块都遵守了原有原则。`contextOrdersFor` 只读公开快照；援军预先登记、入场只是改状态，不是刷兵；通报是数据不是命令。
- 新模块各自有清晰的常量块和前缀（`campaign*`、`fr*`），比老代码容易定位。

没有改善或变差的：

- 仍然全部堆在一个文件里。新模块插在传令兵和分队之间，老代码行号整体后移 115 行，第一版文档里的行号已经失效。
- CSS 又叠了第 6、7 层（38 到 45 行），专门覆盖前几层的字号和布局。
- 出现两套时钟。老的 `isNight`（80 秒入夜）只在关闭战役时用，`campaignClock` 另算；`createState` 里时限和兵力系数也按开关二选一。关闭战役的分支没有任何入口，是死代码。
- 表现层新增 5 个模块级状态变量（`orderContext`、`contextWasOpen`、`reportPicker`、`lastReinforcementFocusId`、`contextSerial`）。`issue()` 现在要同时校验收令人、目标人和情境是否变化。
- `$()` 查询从 157 处增到 209 处，`innerHTML` 整块重写从 16 处增到 18 处。
- 调试接口加了 `report`，但没有战役控制（跳到 540 秒、关闭援军），自动化只能硬跑 900 秒。

### 0.5 新增问题

**问题 16（P1）：观察模式没有出口。** 本部全部撤出或全灭后，游戏继续到 900 秒，玩家只能看。方案：提供“加速”或“跳到援军入场”，或者援军接通即结算。

**问题 17（P2）：两套时钟与死分支。** `isNight` 和关闭战役时的时限、兵力分支没有入口。方案：删掉，或者做成正式的“短局 / 长局”两种模式并都可从界面进入。

**问题 18（P2）：情境键只存在于 UI。** 模拟层不知道玩家当时看到的是哪个情境，日志和结算无法回溯“玩家当时有什么选项”。方案：把情境键和选项列表记录进军令对象。

**问题 19（P1）：援军接通判定过松。** 入场点离阳平只有 120 单位，540 秒入场、560 秒即接通，接通后立刻满足“最低目标”。玩法层面的影响见 02 文档第 0 节。第一轮已修复，见 0.6。

### 0.6 第一轮玩法改动对代码的影响（2026-10-27）

玩法改动的内容和验证见 02 文档 0.10 节。代码层面要知道的是：

- **新增辅助函数**，集中放在 `const CONTROLLED` 之前：东林伏击区判定、敌占据点列表、盟军收拢点、守军不出城判定、魏延判断街亭是否已弱。
- **`routeTo` 增加第三个参数**，传入要绕开的据点，每经过一个加 400 的路程代价。部队、分队和传令兵三处寻路都已传入。
- **新增军令 `camp`（守别营）**，同时写进任务表、方向表和军令文案表。这又是第 4 题说的三套文案表要同步改的例子。
- **新增单位字段** `garrisonSite`、`retreatTarget`、`rallyPoint`，继续加重第 8 题的“状态无结构”。
- **新增地图数据**：路网节点“山西小道”和“汉水渡口”、一处渡口、三条边。这些路线只用于寻路，画面上的图绘没有对应道路。
- **性能**：寻路避让只在重算路线时执行，实测每步耗时与改前同一量级。
- **测试**：`window.__battle` 无法改开局部署，阳平可达性实验只能临时改代码再改回。建议在第 5 题的测试工具里给 `createState` 增加可注入的开局参数。

### 0.7 第二轮玩法改动对代码的影响（2026-10-27）

玩法改动的内容和验证见 02 文档 0.11 节。代码层面：

- **传令**：`dispatchOrder` 增加旗鼓即刻送达的分支，军令记录增加 `transport` 和 `eta` 字段。`stepMessenger` 增加截击逻辑，`moveUnit` 记录部队速度 `vx`、`vy`。新增 `recallOrder` 撤回在途军令。
- **王平**：`stepCommanders` 增加护卫后撤，新字段 `coverUntil`、`coverVec`、`lastWarnHp`，由 `formationSlot` 和 `duelWilling` 读取。新增 `wangpingDangerCouncil`，在 `pollCouncil` 的开局军议之后检查。
- **自动整队**：新增 `fallbackPost`，替换了三处系统改令为“就地整队”的地方。
- **观察模式**：`pump` 增加观战倍率 `observerSpeed`，加速时每帧最多跑 14 毫秒的步数。`catchingUp` 在加速观战时不再报“战况同步中”。
- **调试接口**：`window.__battle` 新增 `recall` 和 `speed`，`getUI` 新增 `observerSpeed` 和 `observing`。
- **测试经验**：做 A/B 对比时，把第一轮版本临时放进 `public/` 与新版并排跑同一脚本，比较结果后删除。

### 0.8 撤守阳平改动对代码的影响（2026-10-27）

玩法改动的内容和验证见 02 文档 0.12 节。代码层面：

- **新任务 `yangping_hold`**：故意不放进 `TASKS` 和 `DIRECTION_LABELS`，所以玩家无法直接下达，只由 `updatePlayerDirections` 在撤守部队抵关时设置。`ORDER_LABELS` 有它的文案。读这个任务的地方有十余处：行军目标、斥候、单挑意愿、弃军判定、军令可用性、情境菜单、观战判定、结算和军议候选。以后再有“锁定”类状态，宜改为单位上的独立字段，不再借用任务名。这是第 8 题“状态无结构”的又一例。
- **撤离判定**：`stepSoldier` 中两处撤离条件收窄为王平本人和护卫，按 `commanderId`、`guardFor` 识别。
- **观战判定**：`ownObserverMode` 改为看本部各军的任务，不再只看兵员统计。
- **测试工具的时间基准**：`frame(now)` 用动画帧时间戳调用 `pump`，其他入口用 `performance.now()`。平时两者只差几毫秒，没有影响。测试替换 `performance.now` 冻结时钟后，页面已排程的那一帧仍会触发一次，把 `lastTick` 拉回真实时间，于是积压出几十秒的步数，`catchingUp()` 变真，军令被拒收。测试脚本已改为等这一帧过去再开局，并逐批记录积压。代码上建议 `frame` 不用传入的时间戳，统一调 `performance.now()`；或在第 5 题的测试工具里提供正式的“推进 N 步”接口。

## 2. 问题与优化建议

每条按 现象 / 影响 / 方案 写。优先级：P0 结构性、P1 需要专门排期、P2 顺手修。

### 2.1 结构与工程

**问题 1（P0）：单文件、超长行、无法协作**

- 现象：所有逻辑在一个 IIFE 里，CSS 和 JS 都被压成单行，最长一行 1.6 万字符。
- 影响：无法 diff、无法并行开发、编辑器卡顿、错误堆栈只能定位到行不能定位到函数。任何改动都要在 900 KB 的文件里搜索。
- 方案：按 1.1 的分层拆成 ES 模块（目录见第 3 节）。先用 Prettier 格式化并提交一次“纯格式化”提交，再拆文件。发布时再由构建工具压缩，源码永远保持可读。

**问题 2（P0）：二进制资源以 base64 内嵌**

- 现象：地图 560 KB、头像 73 KB 都是 `data:image/webp;base64`。
- 影响：base64 比二进制大 33%；浏览器不能单独缓存图片；首屏必须先解析完 900 KB 文本才能开始跑脚本；改一张头像要重新生成整个 HTML。
- 方案：移到 `assets/map-1085.webp`、`assets/portraits/*.webp`，用 `<img>` 或 `fetch` 加载。`MAP_ART_META.sourceSha256` 的校验思路可以保留，改成构建时校验。

**问题 3（P0）：CSS 五层覆盖**

- 现象：第 7 行是浅色主题基础样式；10-13 行改成“指挥台”布局；17-19 行把军议塞进战场；23 行整体换成漆黑主题；26 行再加深；35-36 行用 `position:fixed/absolute` 把整个布局改成全视口 HUD。每一层都在覆盖上一层。
- 影响：前三层的 grid 布局已经是死代码；同一个选择器在 5 处定义，改一处不知道会被哪一层覆盖；浅色主题变量表完全没有用。
- 方案：以第 35-36 行的全视口布局为准重写一份 CSS：一张主题变量表 + 组件样式 + 三个断点。删掉浅色主题，或者改成 `data-theme` 切换。预计能从 48 KB 减到 15 KB 以内。

**问题 4（P1）：三套文案表与到处散落的魔法数字**

- 现象：`TASKS`、`DIRECTION_LABELS`、`ORDER_LABELS` 三张表描述同一组任务；规则数字散落在逻辑里（接应 5 人/75 单位/4 秒、占领 10 人/12 秒、视野 78/125、军议 28 秒过期），UI 的 `TASK_NOTES` 和序幕文案又把这些数字手写了一遍。
- 影响：调一个数值要改两三处，文案和规则会漂移。
- 方案：建一个 `RULES` 常量表集中所有规则数字，文案用模板从 `RULES` 生成；三张任务表合并成一张，字段包含 `label`、`shortLabel`、`group`、`note`。

**问题 5（P1）：没有测试和工具链**

- 现象：没有 `package.json`、lint、测试、CI。README 只有两个词。本机 PATH 里也没有 git 和 node。
- 影响：任何重构都没有安全网。
- 方案：最小工具链 Vite + Vitest + Prettier。第一条测试就是“固定 seed 跑满 420 秒，结果快照的 hash 不变”，拆文件和优化性能时用它兜底。模拟层拆出来后可以在 Node 里无头运行，不需要浏览器。

### 2.2 模拟内核

**问题 6（P1）：每步开销高，手机上会吃紧**

- 现象：实测开局 18 ms/步、中期 6 ms/步，模拟占主线程 6% 到 18%。手机 CPU 慢 3 到 5 倍，开局会到 50 ms/步以上。
- 热点（每步、每个士兵）：`stepSoldier` 先 `nearby` 扫网格，再对每个候选做 `sightRadius`（查地形）和 `lineOfSight`（每 18 单位采样一次 `heightAt` 和 `terrainAt`）；`walk` 里 `terrainAt` 两次、`slopeMovement` 再算两次 `heightAt`；`updateIntel` 每秒对 1280 名士兵做 `canSee`，每次 `canSee` 又是一次 `nearby(160)` 加视线；`playerSnapshot` 每次 pump 都重建 1280 条士兵记录，并对每个敌兵做 `canSee`，还要跑 `coordinationView` 里的 `suggestCoordination`。
- 方案，按收益排序：
  1. 快照改为懒计算：pump 不再 `refreshView`，由 `updateUI`/`draw` 在需要时取，一帧最多算一次，并复用对象而不是每次 `map` 新建。
  2. 视线分级：非交战士兵每 3 步检测一次；视线结果按 (起点格, 终点格) 量化后在一步内缓存；`canSee` 的 key 用整数而不是拼字符串。
  3. 地形和高程查表：`terrainAt` 的 `Map<string>` 改成一维 `Uint8Array` 索引；`heightAt` 预烘焙到更细网格后直接读。
  4. 同一部队的士兵共享一次 `nearby` 结果。
  5. 目标：桌面 5 ms/步以内，手机 15 ms/步以内。

**问题 7（P1）：追赶卡顿**

- 现象：`pump` 一次最多补 35 步，按 18 ms/步就是 630 ms 的同步阻塞。切回标签页或从后台恢复时会卡一下。
- 方案：按时间预算补步，每帧最多 10 ms，补不完留到下一帧（`acc` 机制已经有了）。后台时降到每秒 2 步并在 UI 标注“追赶中”（已有 `catchingUp` 提示）。

**问题 8（P1）：状态对象没有结构**

- 现象：`s` 和每个 `u` 上临时字段很多（`engaged`、`recovery`、`cautiousUntil`、`meeting`、`attackOrder`、`masuPlan`、`supportUntil`……），在不同函数里随手挂上。
- 影响：不知道哪些字段必须序列化，存档、回放、调试都困难；`structuredClone` 会把私有 Map 也带上（当前靠下划线前缀约定区分）。
- 方案：用 JSDoc 或 TypeScript 给 `State`、`Unit`、`Soldier`、`Order`、`Council` 定义类型；把“战术临时状态”放到独立的 `tactics` 子对象；私有索引（`_units`、`_grid`）在快照时显式排除。

**问题 9（P2）：日志上限 90 条**

- 现象：`note()` 超过 90 条就丢最早的，UI 只显示最近 28 条。
- 影响：一局结束后看不到开局发生了什么，结算也无法回放关键节点。
- 方案：上限提高到 500 并按类型筛选；结算时输出完整时间线。

**问题 10（P2）：依赖注入与直接调用混用**

- 现象：传令兵模块通过 `messengerAPI()` 接收函数包，分队模块也接收 `{walk,routeTo,…}`，但同一文件里其他模块直接调用全局函数。
- 方案：拆模块后统一为 import，去掉 API 包。

### 2.3 表现层

**问题 11（P1）：innerHTML 拼接 + JSON 签名做脏检查**

- 现象：`renderGenerals`、`renderOrders`、`renderCouncil`、`renderAllies` 等每 180 ms 把一大块状态 `JSON.stringify` 成签名，签名变了就整块重写 `innerHTML`。
- 影响：序列化本身有开销；整块重写会丢失焦点和滚动位置，屏幕阅读器会重复播报。
- 方案：细粒度比较（只比较用到的字段）加按节点更新；或引入一个 3 KB 级别的模板库。按钮列表这类稳定结构只更新 `textContent` 和 `class`。

**问题 12（P2）：`$()` 反复查询**

- 现象：157 处 `$('id')`，大部分在每帧执行的函数里。
- 方案：启动时缓存一次元素引用。

**问题 13（P1）：绘制全量重绘**

- 现象：`draw` 每 50 ms 清空 700×500 的像素画布，重画全部士兵、火光、箭矢、迷雾、标签，再放大到屏幕。
- 方案：分层画布：地形和图绘静态层只画一次（已做）；迷雾层只在视野集合变化时重算；单位层每帧；标签改为 DOM 或只在变化时重画。夜间火把光晕用预渲染精灵。

**问题 14（P1）：移动端地图被压扁**

- 现象：`syncBattleViewport` 用 `min(宽/1400, 高/1000)` 整体等比缩放，375 px 宽时地图只有 268 px 高，不到屏幕五分之一，HUD 占了其余空间。
- 方案：窄屏按宽度适配并允许纵向滚动/缩放（`zoomed` 类已有基础）；指挥台默认折叠成一条，点开再展开；军议改成底部抽屉。

**问题 15（P1，bug）：结束后迷雾不解除，结算和地图自相矛盾**

- 现象：三局推演都出现这个矛盾。无操作局结算写“列柳：敌军占据”，同一时刻地图和目标条仍显示列柳为蜀军控制；全军撤回局结算写街亭已失，地图仍显示蜀军。原因是 `finish` 用真实状态判定，`playerSnapshot` 在 `outcome` 存在时仍按视野过滤 `sites`。
- 方案：`outcome` 存在时快照直接给真实状态，并在结算页标注“战后核实”。

### 2.4 小问题清单（P2）

- `setPaused` 永远返回 false，是空壳；要么删掉，要么实现。
- 注释里留有协作痕迹（“approved by root”“User's red-box placement”），应改成正式注释。
- 没有 favicon，每次加载一个 404。
- `uiCouncilArchive`、`councilRead` 无上限，长时间开着会缓慢增长。
- `getState()` 每次 `structuredClone` 整个快照，做自动化时每秒多次调用会有开销，可以提供浅拷贝版本。
- 敌军单位快照没有 `task` 字段，与友军字段不一致，消费方要判空。
- 文案全部硬编码在模拟层（`note()` 的中文），以后要做多语言或改文风必须动逻辑代码。
- `.claude/launch.json` 和 `.claude/serve.ps1` 是本次分析为了预览加的，可以进 `.gitignore` 或删除。

## 4. 分阶段路线

| 阶段 | 内容 | 风险 | 验证 |
|---|---|---|---|
| A | 格式化、资源外置、CSS 合并、加 README | 极低 | 页面打开一致，seed 回放 hash 不变 |
